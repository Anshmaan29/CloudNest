# Catalog filesystem safety

Catalog startup creates missing directory components through anchored directory descriptors and refuses symlink ancestors. The final directory must be owned by the current user, mode 700, and have no additional ACL. Main database, WAL, SHM, and rollback journal are checked together before any permission adjustment or migration: regular files, current owner, one hard link, no cloud placeholder, and mode 600. Mode 644 is accepted only as the known legacy layout inside the already private directory; each legacy file is rechecked through its descriptor before tightening it to 600. Shared writable, special, linked, and foreign-owned files are refused without changing them.

New database creation is exclusive and mode 600. SQLite then opens without CREATE and with [SQLITE_OPEN_NOFOLLOW](https://www.sqlite.org/c3ref/open.html). Before reading the schema or migrating, the anchored directory and database identities must still match, and SQLite's [HAS_MOVED file control](https://www.sqlite.org/c3ref/c_fcntl_begin_atomic_write.html) must confirm its opened file has not moved. Failed SQLite handles are closed. Sidecar types, ownership, links, and private permissions are checked again after migration.

Already private database files are checked with anchored metadata operations rather than opening an extra POSIX descriptor. Closing an unrelated descriptor for a SQLite inode can release the process's POSIX byte-range locks. Legacy permission tightening is intended for startup before opening that legacy database in the process; modern reopens avoid those auxiliary descriptors.

These guards protect against linked files, accidental shared paths, and path substitution detected during startup. A program running with the same user identity can already modify the owner's private files; this is not a sandbox against a compromised owner account. SQLite's own journaling and locking remain responsible for ordinary concurrent database access. No user source trees are deleted by initialization.

`CatalogSafetyTests` use generated fixtures only. They verify main-file and every sidecar symlink/hardlink rejection with unchanged foreign bytes and permissions, unchanged legitimate main permissions when a sidecar is unsafe, safe ancestor handling, private legacy migration preserving an unrelated table, and FIFO/shared-writable-file refusal.
